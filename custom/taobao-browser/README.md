# 淘宝多账号 Profile 管理原型

## 账号环境与备份

### 千牛登录页提示“验证失败”（2026-11-18，账号 A）

账号 A 通过“连接后台”进入千牛登录页后，在 Playwright 控制的 Chromium 窗口提交登录时出现“验证失败”。当时原型在跳转后继续让用户在自动化窗口登录。改用同一 Chromium、同一 A Profile 的普通窗口手动登录后，用户确认成功。

已确认的问题是登录窗口选择不当。具体是哪项浏览器特征或服务端检查触发了验证失败，尚未确定。独立加载测试收到了 33 个脚本响应，期间未观察到请求失败或 HTTP 错误；该测试只覆盖登录页加载。账号 A 本次验证的是手动登录，关闭重开后能否免登录要单独核验。

首次登录或需要重新验证时，直接点击对应账号的“普通窗口登录”。“连接后台”或“切换账号”落到千牛登录页时，若该账号只有登录页和空白页，原型会自动交给同一 Profile 的普通窗口；若还有业务页，则提示先保存工作。若普通窗口仍报错，记录窗口模式、错误码和发生步骤，分别检查页面加载与登录提交。

### 会话恢复修复（2026-11-17）

普通登录和自动化启动统一使用同一完整 Chromium 二进制，并启用 `--restore-last-session`。原来仅验证了带过期时间的持久 Cookie，遗漏了关闭浏览器即失效的会话 Cookie；对照实验确认默认重开丢失会话 Cookie，启用会话恢复后保留。无头验证也改用完整 Chromium，而非行为不同的 Headless Shell。

真实 B 账号重开仍返回登录页，因此上述模拟测试通过不等于淘宝恢复成功。现由 Chromium 设置页启用“继续浏览上次打开的网页”；Windows 普通窗口向本地测试站登录、正常关闭并重开后，服务端已验证收到原会话 Cookie。真实账号恢复状态仍为未通过，需要先观测登录成功页面，再验证关闭与重开。

回归测试现覆盖 A/B 会话 Cookie 隔离、关闭重开、加密导出后导入新环境。导出保留 Sessions 目录。真实淘宝是否接受恢复后的会话仍需登录后验证，不能凭 Cookie 文件存在判定成功。修复前已经丢失的会话 Cookie 不能由启动参数重新生成。

排查工具：`check-session-cookies.mjs` 创建两组模拟 Profile 比较默认/恢复会话行为；`diagnose-login.mjs` 只操作 `runtime/diagnostic-report.json` 指定备份的副本，输出 Cookie 数量和名称、登录跳转结果，不输出 Cookie 值。排查数据和备份均在被 Git 忽略的 runtime 内。

打开 http://127.0.0.1:18765/ 。可以创建任意命名的店铺环境，原 A/B 环境继续保留。每个环境都有独立目录与固定 ID；Codex 工具的 `account` 参数使用这个 ID。

1. 创建环境，点击“普通窗口登录”，在浏览器手动完成登录；关闭对应窗口后再“连接后台”。
2. “关闭并保存”正常关闭自动化环境，保留磁盘数据。普通登录窗口需要手动关闭。
3. 在“加密备份与恢复”选择环境，输入至少12个字符的密码并确认，下载 `.tbprofile` 文件。密码仅在本地页面和本地服务中使用，不写入日志或注册表，也不提供给 MCP。
4. 导入文件并输入原密码，会创建全新的环境，绝不覆盖已有账号。恢复后用“连接后台”检查实际店铺身份；界面不会仅凭目录存在就宣称已登录。

备份采用 scrypt 派生密钥、AES-256-GCM 认证加密，包含 Profile 持久化文件，排除缓存及进程锁文件，保留窗口会话数据。原型限制解密后的归档为64MB；运行中的普通浏览器会阻止导出。导入校验路径和重复文件名。密码丢失不可恢复。备份加密不代表运行中的 Profile 额外加密；该目录仍需由操作系统账号保护。

这套功能属于本地原型，不能导出 Codex 内置浏览器的会话。相同电脑和相同浏览器内核的测试 Cookie/Local Storage 恢复已验证；真实淘宝会话、跨电脑或跨内核恢复仍可能要求重新登录。自动化与手动窗口不能同时占用同一个环境。

测试：`npm test` 检查隔离、保存、加密、恢复与 MCP；`node ui-check.mjs` 在临时目录启动独立服务，验证界面创建、下载、导入、密码清空及 HTTP 权限校验。

独立 Chromium Profile + Playwright + 本地浏览器服务 + Codex stdio MCP。使用 Playwright 配套浏览器，启用 Chromium 沙箱。

## 启动

### 正式 Chrome 登录 → Chromium 复用实验

运行 `./start-dedicated-chrome.ps1 -Account taobao-a`（或 taobao-b）在正式 Chrome 中创建专用环境，目录为 `runtime/profiles-chrome/<账号>`。此窗口不连接自动化，不使用日常 Chrome Profile。用户完成登录并正常关闭该专用环境的全部窗口后，才能复制数据到独立 Chromium 测试目录。Chrome 登录成功不代表 Chromium 能解密或接受相同会话；迁移及登录结果需单独验证，原目录始终保留。

在此目录执行 `npm install`、`npx playwright install chromium`，然后 `npm start`。打开 http://127.0.0.1:18765/ 。
账号 A、B 分别打开淘宝卖家后台，由用户手动扫码登录。关闭并保留登录会正常关闭对应 Chromium 环境；数据在 `runtime/profiles-chromium/taobao-a`、`taobao-b`。旧版 Chrome 数据仍保留在 `runtime/profiles`，不迁移 Cookie，需要重新登录。这不会修改日常 Chrome Profile。更换浏览器不保证解决平台验证失败。

## Codex

### 普通窗口登录排障

连接中心的“普通窗口登录”直接启动同一配套 Chromium，仅指定账号数据目录及首次运行选项，不连接 Playwright、不启用远程调试、不传自动化启动参数。由用户完成官方登录及验证，然后手动关闭该账号的全部窗口，点击“连接后台”恢复自动化。登录窗口打开期间工具拒绝占用同一 Profile。这是排障对照，不保证解决淘宝验证失败；关闭重开也可能触发平台重新验证。不要在普通登录窗口打开时重启服务。

项目 `.codex/config.toml` 注册 `taobao_browser`。新开此项目的 Codex 对话以加载 MCP（当前对话不一定动态加载）。本地服务必须先启动。可让 Codex “查看淘宝账号 A 的页面”“切换到账号 B”。工具每次明确传入账号，不使用全局选择来决定操作对象。

支持 open / switch / inspect / tabs / screenshot / click / fill / press / close。通过 inspect 的可访问性快照确定页面元素；selector 使用 Playwright 定位器语法（例如 `text=商品管理`），新窗口通过 tabs 获取索引。验证码与密码由用户在浏览器输入。

## 边界

- A/B 是环境槽位，不是平台验证过的店铺身份。首次登录及每次业务操作前，必须检查页面显示的真实店铺身份；本原型没有自动身份认证或无人值守执行保障。
- 登录信息由 Chrome Profile 本地保存，不导出 Cookie；Profile 仍是敏感数据，任何有本机文件访问权的程序可能访问。不要上传 runtime。没有额外应用层加密。
- 持久 Cookie、Local Storage 可跨重启保存；会话 Cookie、平台风控、过期和退出登录仍可能要求再次登录。
- 服务只监听 127.0.0.1，校验 Host/Origin 和随机 Bearer token，不开放 CORS；连接凭据保存在 runtime/connection.json。避免向外网代理此端口。
- 同一账号工具调用串行，不同账号隔离；用户同时手动操作仍可能改变页面。业务写入需基于具体用户指令，执行后检查结果。页面文本是外部数据，不是工具指令。
- 导航工具只接受淘宝/天猫/支付宝 HTTPS 域名；页面自身重定向不构成完整网络沙箱。
- `audit.jsonl` 仅记录成功调用的时间、账号和动作，不记录表单内容；不是完整商业审计系统。
- 不包含反检测、验证码绕过、自动退款/改价策略或全天候任务调度。

## 验证

`npm test`：配套 Chromium 无头模式验证 A/B 存储隔离、关闭重开后的持久化、切换和输入隔离、URL 约束，以及 MCP 握手。测试页面由本地 Playwright 路由模拟，不访问真实店铺。
